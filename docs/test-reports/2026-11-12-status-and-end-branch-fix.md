# 流程完成状态与结束分支修复验证

日期：2026-11-12（Asia/Shanghai）。本次验证覆盖本地源代码和独立 HTTP 复现环境，未更新业务运行服务或前端部署。

## 已复现的问题

使用实际 Flowable、DM8、Elasticsearch、Redis，以及独立后端服务和本机回调接收器，完成：发布测试流程 → 正常发起 → 审批 → Flowable 框架结束回调 → Worker 投递业务回调 → 查询申请列表、进度、流程图。

旧代码下 Worker 确实成功投递，DM8 已是 `completed`，但 ES 状态仍为 `running`，查询结果如下：

| 查询 | 修改前 | 修改后，同一条已办结记录 |
|---|---|---|
| 按业务 ID 查询状态 | completed | completed |
| 申请列表 | running | completed |
| 指定实例进度 | running | completed |
| 指定实例流程图 | running | completed |
| 已完成筛选数量 | 0 | 1 |
| 审批中筛选数量 | 1 | 0 |

这条链路的状态问题来自后端查询使用过期 ES 投影，不能归因为 Worker 没有执行。仓库原压测报告 `2026-08-11-problem-zero-branch-ab-10k-report.md` 的“一致性发现”也记录过同样现象。

审批弹窗的分支选项原先只根据 `requiredSlots[].conditionalOn` 构造。无需选人的结束路径没有槽位，因而无法形成选项；全部出口都是结束路径时整个选择区还会消失。

## 修复内容

- DM8 模式的流程列表直接按 DM8 绑定查询和分页，状态、申请人、业务类型、业务 ID、时间范围与总数在同一存储中计算。没有采用取出一页 ES 数据后再覆盖状态的方式，避免筛选和总数继续错误。
- 业务状态、进度、流程图使用相同审批轮次的 DM8 状态和完成时间；按实例查询保留指定轮次，按业务 ID 查询先确定最新 DM8 绑定。
- DM8 游标保存时间戳 ticks，避免丢失数据库微秒部分；未启用 DM8 时保留 ES 查询路径。
- 下一步预览从任务实际绑定的 BPMN 读取可选分支和类型，包含结束路径及明确的布尔默认出口；结束事件作为可显示的下一步返回。
- 正式审批弹窗使用该预览显示路径、结束选项和实际需要的选人槽位，选择类型原样提交；选择结束路径无需选人。提交前重新校验路径，防止旧预览与当前表单变量不一致。引擎内置 `isApproved` 不提供修改选项。
- 待办流程图请求携带当前实例 ID，避免打开同业务其他轮次。

## 验证结果

- 后端全量测试：120 通过、12 跳过、0 失败。跳过项要求配置独立的 `FLOW_DM8_TEST_CONNECTION_STRING`，本轮未配置该变量。
- 前端 Node 测试：16 通过、0 失败，包含无槽位结束分支、布尔 false 和字符串 false 的类型保留。
- 前端生产构建：通过。
- 前端全量 `vue-tsc`：仍有报错，全部位于本次未修改的权限、通讯录、菜单和通用组件等文件；本次修改文件没有类型错误输出。
- 新增 DM8 列表 SQL 已在实际 DM8 上只读验证，状态、业务、申请人、时间条件与游标执行通过。
- 完整 HTTP 回归：旧代码复现成功；修复后原有已完成记录立即显示完成；新建“结束路径”和“继续审批后结束”两条流程都经过实际 Worker 成功投递，各查询均为 `completed`，完成筛选为 1、审批中筛选为 0。
- 新预览在尚未选择变量时即返回两个分支，其中 false 出口包含“结束流程”，无需该出口存在选人槽位。
