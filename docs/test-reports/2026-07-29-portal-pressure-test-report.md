# 门户资讯审批极限压力测试报告

> 本文件保留改造前基线。改造后的真实验收、迁移和停止门禁见
> `docs/2026-07-29-flow-runtime-data-and-callback-final-acceptance.md`。

## 结论

当前故障的首要原因不是缺少 ClickHouse 或 Redis 缓存，而是末节点回调
仍在用户完成任务的同步事务链路内。Flowable 的 HTTP ServiceTask 等待
框架回调，而框架回调又同步等待业务回调。测试环境约 5 秒发生 HTTP
超时，导致 Flowable 完成任务返回 500。

在解决同步回调、Flowable 持久化数据库和待办查询分页之前，不建议用
ClickHouse 或大范围 Redis 缓存掩盖问题。

## 测试环境

- 测试服务器：16 CPU、62 GiB 内存；
- Flowable 7.2 容器：`JAVA_OPTS=-Xmx512M`；
- Flowable 未配置外部数据库或数据卷，当前为镜像默认嵌入式存储形态；
- Elasticsearch 与 Redis 为独立容器；
- 流程中心为 Linux self-contained 发布，监听 `:5012`；
- BPMN：`portal_content_approval`，部署版本 4；
- 鉴权：使用一个真实 Keycloak JWT；没有创建 1 万个真实身份。

因此本报告能证明同步阻塞和失效传播，但不能作为生产数据库的最终容量
验收。

## 代码链路证据

`TaskExecutionAppService.CompleteTaskAsync` 先等待 Flowable
`CompleteAsync`。末节点推进至 BPMN HTTP ServiceTask 后，Flowable
同步等待 `/api/callback/flowable`。该接口再等待业务完成回调。用户请求
只有在上述调用返回后才能完成。

异常虽然在部分“安全回调”方法中被捕获，但 `await` 仍会占用请求生命周期；
“不抛异常”不等于“后台执行”。

## 阶梯结果

### 第一档

- 10 个流程启动、10 次待办查询、2 条完整流程；
- 24/24 检查成功，HTTP 失败率 0；
- 末节点 A 组完成约 1.302 秒。

### 第二档

- 100 个流程启动、100 次待办查询、20 条完整流程；
- A/B 各半，B 组延迟 5 秒；
- 启动、发起节点完成和待办查询均成功；
- 末节点完成 8/20 返回 HTTP 500；
- A 组完成：平均 1.840 秒，P95 3.038 秒；
- B 组完成：平均 6.293 秒，P95 6.831 秒；
- Flowable 日志明确出现
  `java.net.SocketTimeoutException: 5000 MILLISECONDS`；
- 慢业务回调峰值并发仅 5 时已经发生失败；
- Flowable 采样峰值约 434% CPU、442.2 MiB 内存。

### 第三档

- 目标：500 个流程启动、100 条完整流程、1000 次待办查询；
- 最高 250 VU，B 组延迟 15 秒；
- 150 个初始 VU 后即进入全局停滞；
- 中止前仅完成 200 次启动尝试和 200 次查询尝试，全部达到 60 秒请求
  超时，未能成功进入末节点；
- 流程中心健康/指标接口也连续超时；
- 观察到约 491 个 `CLOSE_WAIT`、244 个 `FIN_WAIT_2`；
- ASP.NET 线程数最高观察到 340，RSS 在恢复后继续升至约 551 MiB；
- Flowable 内存升至约 468.8 MiB，接近 512 MiB 堆上限；
- 停止压测后约 56 秒服务恢复，待办查询恢复为约 28 ms。

停止临时服务前的最终采样中，待办查询已恢复为约 20 ms，但 Flowable
容器内存（包含堆外内存）达到约 559.9 MiB，说明积压请求仍在后台消化。

由于第三档已出现系统级不可用，未继续执行 5 万目标。继续放大会重复
同一失效模式并污染共享测试环境，不能增加有效容量信息。

## 架构建议

### P0：末节点回调改为持久化异步

框架回调只做状态落库和持久化入队，成功后立即向 Flowable 返回 2xx。
后台消费者再调用业务系统，并实现幂等键、有限重试、退避、死信和可查询
状态。不能使用进程内 `Task.Run` 代替持久化队列。

若仍使用 Flowable 异步 Job，必须验证 Job Executor、重试、事务边界和
业务幂等；目标仍是用户完成请求不等待业务后端。

### P0：Flowable 使用外部事务数据库

5 万活跃实例不应在当前嵌入式、无卷环境验收。先迁移至受支持的
PostgreSQL/MySQL/DM8 等事务数据库，设置连接池、索引和备份，再进行
真实容量测试。

ClickHouse 不适合作为 Flowable 事务数据库。

### P1：重写待办查询

当前实现分别查询 assignee/candidate 的全部任务，合并去重、批量查 ES，
最后才在内存分页。用户待办越多，单次请求越重。

优先做：

1. Flowable 侧分页和总数查询；
2. 避免为第一页读取用户全部待办；
3. 对候选人/办理人建立可分页的任务读模型；
4. 限制 pageSize、设置超时和并发隔离；
5. 增加按操作维度的 P95/P99、连接池和线程池指标。

### Redis

Redis 可以用于：

- 流程定义版本对应的静态节点语义/锚点配置缓存；
- 1 至 5 秒热点待办页缓存，但必须在 claim/complete/reassign/reject 时
  精确失效；
- 防击穿、限流和已有的分布式锁。

不建议把运行中任务真相只放 Redis，也不建议长 TTL 缓存“我的待办”。

### ClickHouse

ClickHouse 仅在大规模历史审计、耗时分析、趋势报表和离线聚合需要时引入。
它不会解决同步回调、Flowable 线程饱和或待办在线分页问题。

### 流程锚点查询

流程定义级锚点是低变更数据，继续存 Elasticsearch，并按
`processDefinitionKey + version` 缓存在 Redis 即可。运行时当前节点仍以
Flowable 或可靠任务读模型为准，不应查询 ClickHouse。

## 下一轮验收门槛

修复后再执行 100、1000、5000、10000、50000 的分级测试；每级同时验证：

- 末节点完成接口不受 B 组 15/30/60 秒延迟影响；
- 待办查询 P95/P99 和错误率；
- Flowable/API/数据库连接池与队列深度；
- 客户端断开后的在途请求能快速回收；
- 回调最终成功率、重试、死信和幂等；
- 1 万真实用户模型与单个大待办用户模型分别测试。
